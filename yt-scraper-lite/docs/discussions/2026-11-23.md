# Worker failure handling

2026-11-23. How `yt-scraper-lite/worker.py` treats a crash or non-zero exit from `search_videos.py`, `download_videos.py`, and `speech_ratio.py`.

The worker does not die with the child. It waits, logs the child's status, and either stops the run or goes on to the next URL. A signal death shows up as a negative status (for example `-11`). `sys.exit` of that value becomes an 8-bit shell status.

## search_videos.py

| Failure | What the script does | What the worker does |
| --- | --- | --- |
| Missing `YOUTUBE_API_KEY`, unreadable `.search_run` / `.search_history`, or `YouTubeAPIError` (HTTP error, network error, bad JSON, failed cursor write) | Prints the error to stderr and exits 1. History and cursor are written only after `collect` returns, so a failure inside `collect` leaves them unchanged. | No `https://` lines and no `kept 0` in stderr. Exits with the child's status. Nothing is downloaded. |
| Catalog produced no keepers | Exits 1 after a `kept 0, ...` report, often with `catalog exhausted`. | Not an error. Stops the run when the catalog is exhausted or the cursor did not move. Otherwise fetches another batch. |
| Bad arguments | `argparse` exits 2. | Same as an API failure: exit 2, no download. |
| Killed after history is saved, or exits non-zero after printing some watch URLs | History already contains every kept id. Stdout may contain only part of the list. | Any `https://` line makes the batch a success. Those URLs are downloaded. Ids that were saved but not printed stay in `.search_history`. |

## download_videos.py

`yt-dlp` defaults to stopping on the first error. An uncaught `DownloadError`, a missing interpreter, or `argparse` exiting 2 all end the process with a non-zero status. Files already written stay in the temp directory.

The worker logs `download_videos exited …` and still looks for a finished file per URL. `.part`, `.ytdl`, and `.temp` names are ignored. A URL with no file is logged and skipped. The batch still counts toward `n`, and the run continues. The temp directory is removed in `finally`.

The run stops with status 1 only when the script cannot be started (`OSError`).

## speech_ratio.py

| Failure | What the script does | What the worker does |
| --- | --- | --- |
| Missing file, ffmpeg missing or failing, unexpected wav, Silero load error, any other uncaught exception | Traceback and exit 1, or `argparse` exit 2. | Logs the status, stops the rest of that batch, deletes the temp directory, and exits with the child's status (1 when there is no numeric score). |
| Empty audio | Prints `0.0000` and exits 0. | A real score. The URL is dropped when it is below the threshold. |
| Killed by a signal | Negative status. | Same early exit, using that negative status. |

URLs already printed in the batch stay on stdout. Later URLs in the batch are not scored.

## No status channel

The worker has no authoritative signal from any sub-script. Each script prints logs and an exit code meant for a person, and the worker reconstructs what happened from those side effects.

Search exhaustion is a mixed heuristic. `classify` sets `exhausted` when stderr contains the substring `catalog exhausted`. That phrase is a log line from an empty page or a missing `nextPageToken`, and the summary repeats it when the batch kept fewer than its target. If the batch printed no watch URLs, an unchanged `.search_run` file also counts as exhaustion, including a file that was never written. A batch that kept nothing but moved the cursor is only `search batch empty`, and the worker calls search again. `stopped after … search calls` is a different log line, so the call cap is not exhaustion unless the cursor file happens to be byte-for-byte the same.

The same guessing shows up in the other two scripts. Search uses exit 1 both for an API failure and for a finished catalog, so the worker separates them by looking for `kept 0` in stderr and for `https://` lines on stdout. Download success is a filename in the temp directory that contains `[video_id]`, not the exit code. Speech success is the last non-empty stdout line parsing as a float. A log wording change, a partial stdout, or a cursor rewrite that preserves the same bytes changes what the worker decides.

## Conclusion

Failure handling is uneven, and a failed video is not retried.

Search and speech failures end the run. A download failure does not, so a broken `yt-dlp` setup can walk through all `n` URLs, skip every file, and still exit 0.

`.search_history` is updated when search keeps an id, before download or scoring. The worker only puts ids back when a search batch is longer than the remaining quota. Ids whose download produced no file, and ids left unscored after a speech failure, stay in history. The next run deletes `.search_run` and will not select those ids again.

There is no timeout. A child that never exits blocks the worker until something else kills it. Cleanup of the download directory ignores errors, so a file that is still busy can be left behind after the `deleted …` log line.

None of the sub-scripts can tell the worker, in a field they own, whether the run failed, the catalog is finished, or a video was skipped. Until that exists, the worker will keep treating log text, exit codes, and leftover files as the protocol.
